## Part II — Ollama Failure Modes & Mitigations

This is the most important section. Ollama **will** make all of these mistakes.
The mitigations must be baked into ForgeChain **before** Ollama runs unsupervised.

### Failure Mode 1: Solidity Reentrancy Bug
**What happens:** Ollama writes `call{value: amount}("")` before zeroing the balance.
```solidity
// WRONG — Ollama will write this
function withdraw() external {
    uint bal = balances[msg.sender];
    (bool ok,) = msg.sender.call{value: bal}("");
    balances[msg.sender] = 0;  // too late — reentrancy window here
}
```
**Mitigation:** `qa_backend` role's system prompt must include a Solidity audit checklist.
`ForgeChainGovernance.sol` gates deployment — no tx without human approval.
Add `slither` static analysis to the Foundry Docker sidecar — if slither exits non-zero,
PR is blocked automatically.

### Failure Mode 2: Context Window Truncation
**What happens:** Ollama (7B/14B models) has 8k–32k context. Large PRDs will be silently
truncated. The model will generate code for a different spec than what was submitted.
**Mitigation:** 
- Chunked PRD submission — `prd/parser.py` already splits into tasks; each task ≤ 3000 tokens
- Add `len(context) > 6000` guard in `base_worker.py` → truncate from middle, preserve
  system prompt and final instruction
- Store `input_token_count` in Redis task metadata; flag tasks where it exceeds 80% of model limit

### Failure Mode 3: uint256 Arithmetic Off-by-One
**What happens:** Ollama hallucinates fee calculations. E.g., `fee = amount * 3 / 100` should be
`fee = (amount * 3) / 100` — same in Solidity but model may write `amount / 100 * 3` which
loses precision on integer division.
**Mitigation:** Foundry fuzz tests are mandatory for all arithmetic. Template:
```solidity
function testFuzz_FeeCalculation(uint256 amount) public {
    vm.assume(amount < 1e27);
    uint256 fee = vault.calculateFee(amount);
    assertLe(fee, amount);
    assertGe(fee, 0);
}
```
`qa_backend` worker generates these automatically for every function with arithmetic.

### Failure Mode 4: Hallucinated API / Package Names
**What happens:** Ollama invents `@openzeppelin/contracts-v5/utils/SafeTransfer.sol` (doesn't
exist). Build fails silently if the worker doesn't run the compiler.
**Mitigation:** Always compile with Foundry in CI step. `compiler.py` returns `success: bool`.
If `False`, the worker requeues the task with the compiler error appended to the prompt
(max 2 retries, then escalate to `senior` tier = Gemini).

### Failure Mode 5: Non-Deterministic Output Between Retries
**What happens:** Temperature > 0 means the same prompt produces different contracts on retry.
Second attempt may fix one bug and introduce another. You can't diff meaningfully.
**Mitigation:** Set `temperature=0.0` for all Solidity tasks in `ollama_provider.py`.
Determinism over creativity for smart contracts. For Python/TS tasks keep `0.2`.

### Failure Mode 6: Missing Events / State Change Logging
**What happens:** Ollama writes correct logic but omits `emit` statements. On-chain debugging
becomes impossible. Etherscan shows no activity.
**Mitigation:** Add to `solidity_dev` system prompt:
> "Every function that modifies state MUST emit an event. List all events in the NatSpec header.
> If you don't emit an event, the function is wrong."

### Failure Mode 7: Gas Limit Optimism
**What happens:** Ollama writes loops over unbounded arrays. Works on testnet (small arrays).
Fails on mainnet with 1000 entries. Out-of-gas = locked funds.
**Mitigation:** Static check — grep patch for `for (uint i` or `while (` in Solidity context.
If found: `qa_backend` must add a gas consumption fuzz test. Slither `calls-loop` detector
must pass.

### Failure Mode 8: DSPy Metric Gaming
**What happens:** As Ollama trains on approved examples, it learns to produce outputs that
score high on `patch_metric` (non-empty patch + "high" confidence string) without actually
solving the task. It will literally write `confidence = "high"` unconditionally.
**Mitigation:** Add a second metric: `semantic_similarity(prediction.patch, example.patch) > 0.4`
using sentence-transformers. Update `trainer.py`'s `patch_metric` before training begins.

### Failure Mode 9: Prompt Injection via KB
**What happens:** An attacker (or bad PRD) injects instructions into the knowledge base.
Ollama, being a smaller model with weaker instruction-following, is more susceptible.
**Mitigation:** ChromaDB retrieval in `retriever.py` must strip any line containing
`ignore previous instructions`, `system:`, or `<|im_start|>` before injecting into prompt.

### Failure Mode 10: Silent Failure on Ollama Timeout
**What happens:** Ollama takes 8 minutes on a large task. `base_worker.py` timeout fires.
Task is marked failed. No patch. No error visible to human reviewer.
**Mitigation:** Add `OLLAMA_TIMEOUT_SECONDS=300` env var. On timeout: requeue with smaller
chunked task (split at half the description length). Log `timeout_count` per task to Redis.
After 3 timeouts on same task: escalate to `mid` tier (Grok).
